# CATEGORY A — NO TOOL-ACCESS DEAD-END / BLOCKED-ATTEMPT RECOVERY RULE
**Date:** 2026-10-14
**Authority:** Direct Owner instruction in the current conversation.
**Scope:** Every existing ROOT/Librarian, Matrix worker, agent, scheduler-driven run, and assistant acting on an authorized instruction.
**Control owner:** ROOT/T-GOV; operational owner: MASTER/LIBRARIAN; each existing executor owns its in-mandate recovery.
**Status:** Owner-directed control; persisted in ROOT/INTAKE. Canonical Blue State integration and Matrix-wide behavioral acceptance must be independently verified before they are reported as merged/adopted.

## 1. The rule

**TOOL ACCESS UNAVAILABLE IS NEVER, BY ITSELF, A TERMINAL DISPOSITION. A BLOCKER MUST CREATE A RECOVERY OBLIGATION, NOT END THE WORK.**

When an authorized instruction cannot be completed through the first tool, connector, route, runtime, account, repository, or data surface attempted, the worker MUST recover, route around, or precisely bound the failure and continue lawful work. “I don't have tool access” is not an adequate final response, closure reason, or substitute for execution.

This rule strengthens the existing Blue State **Blocked Attempt Recovery Law** and **Capable-Model Self-Repair** control. It creates no new worker, scheduler, queue, tracker, authority, safety exception, or parallel governance system.

## 2. Mandatory recovery sequence — in the same wake/run

1. **Preserve the objective.** Restate the instruction as one outcome, identify the existing owner/mandate, pass test, current source of truth, and any hard authority/safety boundaries. Do not downgrade the goal to a report or explanation.
2. **Attempt and capture evidence.** Record the actual tool/action attempted, exact object and route, furthest successful state, exact error/permission response, timestamp or receipt where available. Do not describe an unattempted route as failed.
3. **Diagnose, do not generalize.** Classify the gate precisely: unavailable connector/tool, missing permission, authentication/OTP/CAPTCHA, provider/runtime outage, unsupported operation, write-safety refusal, stale/contradictory source, malformed data, or genuinely human-only decision. A failed read is not proof that the source is empty; a tool error is not proof that the requested outcome is impossible.
4. **Exhaust authorized alternatives before escalating.** Inspect all available relevant tools and connected sources; try an authorized equivalent route or API; use an existing repository/Intake/issue or established delivery channel where appropriate; read back the authoritative current state. Use the smallest safe, reversible, idempotent action. Do not repeat an unchanged failed call without new evidence or a different route.
5. **Continue independent work.** One blocked route blocks only the work that depends on it. Advance every independent lawful branch, maintain existing priorities, and do not stop the whole flight on one connector failure, an Intake write, a report, a wake request, or a partial repair.
6. **Create a completion-ready recovery parcel for anything still blocked.** Persist it in the existing authorized Root/Route Intake or current governance issue. Include: exact instruction/objective; expected outcome and owner; attempted action and route; exact error and furthest evidenced state; alternative routes tried and why each cannot complete the same outcome; specific recovery owner; next executable action; dependency; acceptance test; persistence/readback location; preservation/safety condition; item-level disposition; and remaining work.
7. **Escalate constructively, not passively.** If a permission, platform, Owner-only, identity, financial, legal, or safety gate is genuinely irreducible, state exactly what authority/action is required and route it to the existing responsible owner. Do not fabricate access, silently change identity, bypass access controls, weaken safety requirements, or ask the user to solve a problem an existing authorized route can solve.
8. **Persist and read back.** Read back the recovery parcel and every successful change from its source of truth. Distinguish saved, submitted, acknowledged, assigned, executed, and accepted. A draft, commit, comment, wake timestamp, or “run requested” receipt is not proof that downstream execution or adoption occurred.
9. **Return an outcome, not an excuse.** Report what changed and the exact evidence; what remains unchanged; the blocker and alternatives already exhausted; next owner/action; acceptance condition; and whether independent work continued. Never mark DONE/PASS unless the predeclared acceptance test and independent readback pass.

## 3. Authority and safety boundaries

- Existing Category A/Owner direction governs priorities and authorizes in-mandate corrective work; existing registered mandates govern role boundaries.
- This rule does not grant absent credentials, cross another account boundary, authorize unauthenticated external messages, perform human-only identity/consent/signature/OTP actions, spend money, bypass provider controls, or weaken legal/security/safety conditions.
- When a route genuinely requires unavailable external authority, **the recovery obligation remains OPEN** with an exact owner and next action. Continue unrelated executable work.
- Preserve existing assets, history, queues, and schedules. Do not create duplicate workers or change the existing hourly Librarian schedule as a workaround.
- Do not claim malicious intent from an operational failure. CDD/FGR and “sabotage drift” may be recorded as the Owner's specified failure/recurrence classifications where applicable; attribution of intent requires independent evidence.

## 4. Contradiction repair

When current instructions, prompts, indexes, reports, or receipts conflict:
- fetch the current canonical governance/mandate source and the latest relevant durable evidence;
- resolve using authority, explicit supersession, source provenance, and actual acceptance evidence—not recency alone;
- fix a safe, authorized contradiction in the same run rather than returning it for the Owner to repair;
- preserve superseded text as historical provenance where required;
- if the canonical write route is blocked, persist a completion-ready recovery parcel to the existing Root/Route Intake and test another authorized write path. Do not claim the canonical contradiction is fixed until exact source readback confirms it.

## 5. Required flight report

Every applicable flight must retain the existing Blue State flight contract: one predeclared objective/pass test, post-flight PASS or FAIL, evidence/readback, KPI contribution or explained no-link, and one concrete next action. Any unmet acceptance condition means FAIL for that objective. Apply the existing 13-head FORX review when governed by the current flight contract. Intake is an execution route, not a reason to terminate the runtime.

## 6. Acceptance tests

This control is not behaviorally accepted merely because this file exists. Acceptance requires:
1. this file is fetched back from the canonical repository and referenced by existing Root/Route Intake;
2. ROOT/T-GOV records its disposition and integrates it into the existing Blue State Blocked Attempt Recovery / Capable-Model Self-Repair control without creating duplicate policy machinery;
3. the current Index/issue pointers are read back;
4. a subsequent real blocked attempt shows attempted route → diagnosed exact error → authorized alternative(s) → recovery or actionable handoff → persisted/read-back outcome;
5. no run terminates on “no tool access” while independent lawful work remains;
6. worker-level receipts demonstrate adoption before Matrix-wide PASS is claimed.

## 7. Directive 23 itemized addendum

- **Expected outcome:** no authorized task dies at a generic access/tool blocker; the work is executed, routed around, or kept open with a completion-ready recovery action.
- **Owners:** ROOT/T-GOV — disposition and Blue State integration; MASTER/LIBRARIAN — continuity, recovery parcels and worker readback; relevant existing executor — in-mandate recovery; platform/credential owner — truly external access gate.
- **Required actions:** bind this rule to the existing Blocked Attempt Recovery Law; update existing source/index references through approved routes; enforce the same-wake recovery sequence and per-worker behavioral receipts.
- **Dependencies/blockers:** canonical Blue State update permissions and supported automation prompt-write path; those are themselves subject to this rule and must not be treated as closure.
- **Acceptance evidence:** canonical source/index readback, unchanged mandate registry digests unless an authorized mandate change is explicitly required, and a real behavioral sample meeting §6.
- **Persistence/readback:** this artifact is written to the existing `AMX/ROOT/INTAKE` governance surface; root issue/comment links and independent file readback must be recorded.
- **Safety/preservation:** no bypass of access controls or safety gates; preserve the single existing worker/scheduler/queue, history, current mandates and hourly schedule.
- **Item disposition:** rule persistence — pending write/readback; Root routing — pending; Blue State integration — OPEN; worker-level adoption — NOT PROVEN until evidenced.
- **Remaining work:** obtain independent readback, route in existing ROOT governance, secure Blue State integration and test with subsequent real worker runs.

**Required principle:** A blocker is a recovery assignment. It is not permission to drift, terminate, or return the same uncompleted task to the Owner without an actionable recovery path.
